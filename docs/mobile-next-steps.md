## 原建议实施顺序（本批不继续新增功能）

### 1. 收尾当前 UI 与交互回归

先处理仍明确存在的反馈弹窗验收缺口，再覆盖更多 / 设置 / 协议页面的滚动、输入、关闭和返回。检查小屏、大字体、软键盘展开及附件列表变长；Web Phone 与 Native 分别检查，不能因共享组件就推断行为相同。

完成标准：正文能滑到最底部，提交与关闭均可操作；弹窗操作不触发换 Space / 翻页；关闭后原会议与草稿行为正常。iOS 和 Android 分别记录结果。

### 2. 验收已接入的账号流程

用专用测试账号验证：注册发码 → 60 秒重发 → 验证登录 → 重启恢复 / 不记住我 → 找回密码 → 新密码登录 → 更换头像 → 退出。补测错误 / 过期 / 重复验证码、网络中断、刷新竞态与文件选择取消。注销单独核验旧平台已知表和文件清理，不能使用真实日常账号做破坏性回归。

完成标准：真实邮件与接口、App 状态一致；资料与头像刷新后仍正确；失败保留可恢复状态，注销失败不误报成功。先准备测试数据与检查清单；真实发送、上传和删除的具体执行按用户授权处理。

### 3. 打通账号资料与个人房间

这是建议的下一批功能开发，不在此次规划中直接实施：

1. 昵称保存写回旧平台，并让 App / 旧平台读取同一份资料；昵称与唯一 username 分开处理。
2. 先盘点旧平台 space 与会议服务 Space 的标识、创建和删除责任，再设计账号到房主凭据的映射；不能仅凭相同 username 或登录状态授予房主权限。
3. 再接入登录账号创建房间的持久化，使创建成功后能在“我的房间”看到、重启后仍存在，并能恢复正确管理身份。
4. 覆盖重复创建、跨账号访问、部分写入失败 / 重试、退出登录及注销的关联处理；访客临时房间保留现有边界。

完成标准：注册 / 登录 → 创建 → 列表可见 → 重启 → 再进入并确认权限，形成一条可验证流程。房间类型仍只接常规房间。

### 4. 验收会议与广场真实媒体

先用一个测试 Space 验证 Web 与两端 App 的入会、发布授权、摄像头 / 麦克风 / 共享、断网重连、后台和退出，再接真实主会场 HLS。

预览重点：9.9 / 10 秒边界、卡顿不累计、快滑与迟到回调、手动加入和倒计时同时触发只加入一次、Tab 切换停止播放、正式 RTC 前释放 HLS、子 Room 媒体隔离、主持 / 发布者退出确认。小范围通过后再做连续 100 次切换、资源清理与容量问题。

完成标准：有真实播放器与 RTC 交接证据，无双房间正式会话、私密轨道泄露或后台误加入。没有真实预览源时保留手动加入与不可用提示，不以占位画面验收自动加入。

### 5. 形成可发布测试版本

归整当前多批差异，更新 API / Web / App 版本配套说明，补齐 Android 原生构建和设备验证；对最终版本统一跑类型、边界、测试与隔离构建，再验证镜像启动、配置、备份和回退。已有服务和开发构建目录不被验证过程覆盖。

完成标准：新机器可复现安装；已验收和已知限制分开；之后再决定是否进入 TestFlight / 商店准备。此次不代为提交、推送或发布。
